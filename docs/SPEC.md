# QUERY RUSH 仕様書（SPEC）

作成日: 2026-11-16 / ステータス: 仕様段階

## 概要

寿司職人ゲーム × SQL の高速クエリ組み立てアクション。

画面をポチポチしながら高速でSQLを組む。キーボード入力はゼロで、句チップをタップ／クリックして組み立てる。注文票の完成形に結果を一致させるまでの「読む→選ぶ」の速さで競う。

## 共通前提

- プレイヤーが扱えるのは原則 `SELECT` のみ。DBは読み取り専用接続で開く
- 実行制限: 1クエリ 100ms / 取得上限 100行
- 1プレイ完結型
- オンライン対戦・ランキングはMVP外

## 設計上の絶対条件（成立条件）

以下3点はこのゲームの成立条件であり、実装時に崩してはならない。

1. **注文は常時1件だけ（最大2件）**。速さはマルチタスクではなく「データを読む判断の速さ」から作る。同時処理の忙しさは入れない（忙しいリアルタイム操作は好みに合わないため）
2. **チップの配置は固定**（毎回シャッフルしない）。探す時間ではなく、選ぶ時間で勝負させる
3. **同時表示チップは最大8枚**。難化はチップ種類の増加ではなく、データ側の罠（似た列名、NULL、重複行）で行う

## 画面構成

- 上段: 注文票（例「売上が高い順に3件、返品は除く」）と完成形の結果プレビュー
- 中段: テーブル本体。チップを置くたびにその場で絞り込まれてハイライトされる（ライブプレビュー）
- 下段: 句チップの棚

## コアループ

1. 注文が提示される
2. チップを置いてクエリを組み立てる。置くたびにSQLiteで実行し、結果を中段へ即時反映する
3. 結果が注文と完全一致したら「提供」で次の注文へ
4. ミス（不一致のまま確定、または不正な組み合わせ）でコンボが切れる

## モード

- **60秒スプリント（MVPの中心）**: 制限時間内に何件捌けるかのスコアアタック
- ウェーブ制サバイバル: 後半はJOINで2テーブル目が加わる、NULLが混入するなどで難化する。**MVP外**とし、先送りを明記する

## スコア

- 基本: `基本点 × コンボ倍率 ＋ 残り時間ボーナス`
- 速さより「ノーミスで読み切る」方が伸びる配分にする（コンボ倍率の比重を大きくする）
- ミスでコンボ倍率はリセットされる

## チップ例

| チップ | 役割 |
|---|---|
| `WHERE price > 1000` | 条件で絞り込む |
| `WHERE status != 'returned'` | 除外条件（返品は除く等） |
| `ORDER BY sales DESC` | 並び替える |
| `LIMIT 3` | 件数を絞る |
| `JOIN users` | 2テーブル目を結合する（難化要素） |
| `GROUP BY category` | 集計する |

## データ側の罠（難化要素）

- 似た列名（例: `price` と `list_price`、`sales` と `sales_count`）
- NULLの混入（条件から漏れる／含まれるの読み違いを誘う）
- 重複行（DISTINCTや集計の要否を判断させる）

## 勝敗条件

- 勝利／敗北の概念はなく、60秒経過で終了しスコアを確定する
- スコア: 捌いた注文件数、最大コンボ、ミス回数を内訳として表示する

## MVPで作らないもの

- ウェーブ制サバイバルモード
- キーボードによる自由入力モード
- オンライン対戦、ランキング
- チップ配置のシャッフル、同時表示9枚以上のチップ

## 未決事項

- プラットフォーム（Web / Android）は未定。MVPのUIは「クリック／タップできるチップUIを持つ最小GUI」とし、実装技術は Issue #1（Epic）で決める
- 実装言語・フレームワーク
- スコア式の最終形（基本点・コンボ倍率・時間ボーナスの数値）
- ウェーブ制サバイバルの着手時期（MVP完了後に判断）
