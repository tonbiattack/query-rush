# QUERY RUSH 仕様書（SPEC）

作成日: 2026-11-16 / 更新日: 2026-11-16 / ステータス: **MVP実装・検証中**

## 概要

寿司職人ゲーム × SQL の高速クエリ組み立てアクション。

画面をポチポチしながら高速でSQLを組む。キーボード入力はゼロで、句チップをタップ／クリックして組み立てる。注文票の完成形に結果を一致させるまでの「読む→選ぶ」の速さで競う。

## 共通前提

- プレイヤーが扱えるのは原則 `SELECT` のみ。DBは読み取り専用接続で開く
- 実行制限: 取得は最大100行、101行目で打ち切る。100ms超過はコスト超過として不正解扱いとする。SQLiteの同期処理の途中停止はできず、最初の行を返すまでの100msを厳密に強制する機構はMVPでは未実装
- 1プレイ完結型
- オンライン対戦・ランキングはMVP外

## プラットフォームと技術スタック（Issue #1 で確定）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| プラットフォーム | **Web（ローカルサーバー + ブラウザ）** | クリック／タップのチップUIを最短で作り、実プレイ検証まで一気に到達できる。Android実機の準備なしで「判断の速さで遊べているか」を確かめられる |
| 実装言語 | **JavaScript（ESM、Node.js 22.16以上）** | ビルド工程ゼロ。`node:sqlite` が標準搭載なので追加依存なしでSQLiteを扱える |
| DB | **SQLite（`node:sqlite`、読み取り専用接続）** | 仕様どおり。`readOnly: true` で開き、書き込みはエンジン側でも拒否する |
| UI | **素のHTML / CSS / JS**（フレームワークなし） | 3段構成の固定レイアウトにフレームワークは過剰。描画のたびに全行を組み直す方が、ライブプレビューの挙動を追いやすい |
| テスト | `node:test`（標準） | 追加依存なし |

**Android を選ばなかった理由**: 実機ビルド・インストールの手間がMVP検証のボトルネックになるため。チップUIはタッチ操作を前提にした当たり判定とレイアウトにしてあり、必要になれば同じロジック層（`src/engine.js` / `src/game.js`）をそのままAndroidへ移植できる。

## 設計上の絶対条件（成立条件）

以下3点はこのゲームの成立条件であり、実装時に崩してはならない。

1. **注文は常時1件だけ（最大2件）**。速さはマルチタスクではなく「データを読む判断の速さ」から作る。同時処理の忙しさは入れない（忙しいリアルタイム操作は好みに合わないため）
2. **チップの配置は固定**（毎回シャッフルしない）。探す時間ではなく、選ぶ時間で勝負させる
3. **同時表示チップは最大8枚**。難化はチップ種類の増加ではなく、データ側の罠（似た列名、NULL、重複行）で行う

実装上の担保:

- 1 → `createGame` は常に `currentOrder()` を1件だけ返す。テスト「注文は常時1件だけ」で検証
- 2 → `SHELF_LAYOUT`（`src/chips.js`）の並びをプレイ中に変更する経路が無い
- 3 → `CHIPS` は8枚ちょうど。`check:orders` が8枚を前提に全配置を列挙する

## 画面構成

3段構成。上から順に「読む → 確かめる → 選ぶ」に対応する。

- **上段左: 注文票** — 注文文と、その注文で気をつける点（データ側の罠のヒント）
- **上段右: 完成形プレビュー** — 目指す結果。通常行は商品名と並び替え列を、集計はカテゴリ・件数・売上を表示する。判定は全列・全行・順序で行う
- **中段: テーブル本体** — チップを置くたびにその場で絞り込まれてハイライトされる（ライブプレビュー）。上部に組み上がったSQLを常時表示
- **下段: 句チップの棚** — 8枚を固定配置。`WHERE` / `GROUP BY` / `ORDER BY` / `LIMIT` を色分け

## コアループ

1. 注文が提示される
2. チップを置いてクエリを組み立てる。置くたびにSQLiteで実行し、結果を中段へ即時反映する
3. 結果が注文と完全一致したら「提供」で次の注文へ
4. ミス（不一致のまま確定、または不正な組み合わせ）でコンボが切れる

## モード

- **60秒スプリント（MVPの中心）**: 制限時間内に何件捌けるかのスコアアタック
- ウェーブ制サバイバル: 後半はJOINで2テーブル目が加わる、NULLが混入するなどで難化する。**MVP外**とし、先送りを明記する

## スコア

- 基本: `基本点 × コンボ倍率 ＋ 残り時間ボーナス`
- 速さより「ノーミスで読み切る」方が伸びる配分にする（コンボ倍率の比重を大きくする）
- ミスでコンボ倍率はリセットされる

### 確定した数値（`src/config.js`）

| パラメーター | 値 | 意味 |
| --- | --- | --- |
| 【スプリント秒数】 | 60 | 制限時間 |
| 【基本点】 | 100 | 1件提供あたりの基本点 |
| 【コンボ倍率の増分】 | 0.25 | コンボ1ごとに加算 |
| 【コンボ倍率の上限】 | 4.0 | 倍率の頭打ち |
| 【時間ボーナス係数】 | 10 | 1秒あたりの加点 |
| 【時間ボーナス窓秒】 | 8 | この秒数以内の提供に時間ボーナスが乗る |
| 【クエリ制限時間ms】 | 100 | 1クエリの実行制限 |
| 【取得上限行数】 | 100 | 1クエリの取得上限 |

**コンボ倍率** = `min(1 + 0.25 × コンボ, 4.0)`
**時間ボーナス** = `max(0, (8 − 注文提示からの経過秒) × 10)`

例: コンボ0で即提供 = 100 + 80 = 180点。コンボ5で8秒かけて提供 = 100×2.25 + 0 = 225点。**ノーミスで繋いだ方が、速いだけの1件より高い**。

## チップ（8枚・固定配置）

| # | チップ | スロット | 役割 |
| --- | --- | --- | --- |
| 1 | `WHERE price > 1000` | WHERE | 売価で絞り込む |
| 2 | `WHERE list_price > 1000` | WHERE | 定価で絞り込む（似た列名の罠） |
| 3 | `WHERE status != 'returned'` | WHERE | 返品を除く |
| 4 | `WHERE stock > 0` | WHERE | 在庫があるものに絞る |
| 5 | `GROUP BY category` | GROUP BY | カテゴリで集計する |
| 6 | `ORDER BY sales DESC` | ORDER BY | 売上金額で並べる |
| 7 | `ORDER BY sales_count DESC` | ORDER BY | 販売数で並べる（似た列名の罠） |
| 8 | `LIMIT 3` | LIMIT | 件数を絞る |

`WHERE` は複数枚を AND で積める。`GROUP BY` / `ORDER BY` / `LIMIT` は各1枚まで（同じスロットの別チップを押すと差し替わる）。

## データ側の罠（難化要素）

`src/data.js` のシードデータに仕込んである。**どの罠も「チップを1枚外す／差し替えると結果が変わる」ことを `check:orders` が機械的に検証する。**

- **似た列名**: `price`（売価）と `list_price`（定価）、`sales`（売上金額）と `sales_count`（販売数）。`price > 1000` と `list_price > 1000` はどちらも単独で一意な結果になり、互いに別の行集合を返す
- **NULLの混入**: `price` が NULL の行（穴子・白身）、`stock` が NULL の行（中とろ・白身）。NULL は比較条件で弾かれるので「在庫あり」に含まれない
- **重複行**: `sales` が同値の行（茶碗蒸し・だし巻き）。`ORDER BY` には必ず安定キー（`id` / `category`）を足して並びを一意にする
- **返品**: `status = 'returned'` の行が売上上位に混ざる（えび・大とろ・天ぷら）。「返品は除く」を読み落とすと上位3件が変わる

## 注文

10件を定義（`src/orders.js`）。難易度は罠の密度。

| ID | 注文 | 難易度 |
| --- | --- | --- |
| o1 | 返品は除く。売上の高い順に3件。 | 1 |
| o2 | 1,000円を超えるもの。売上の高い順に。 | 2 |
| o3 | 在庫があるもの。販売数の多い順に。 | 2 |
| o4 | 返品は除く。1,000円を超えるもの。売上の高い順に。 | 2 |
| o5 | 返品は除く。カテゴリごとの売上合計。売上の高い順に。 | 3 |
| o6 | カテゴリごとの件数。件数の多い順に3件。 | 3 |
| o7 | 定価が1,000円を超えるもの。売上の高い順に。 | 3 |
| o8 | 在庫があり、返品は除く。売上の高い順に3件。 | 2 |
| o9 | 1,000円を超え、在庫があるもの。売上の高い順に。 | 3 |
| o10 | 在庫があるもの全件。売上の高い順に。 | 1 |

### 注文の生成条件（Issue #4 の受け入れ条件）

`npm run check:orders` が全192通りの配置を実行して次を検証する。

1. **解ける** — 完成形のクエリがエラーにならず1行以上返す
2. **一意** — 完成形と同じ結果になる別の配置が存在しない
3. **全チップ必須** — 完成形からチップを1枚外すと結果が変わる（無駄なチップが無い）
4. **罠が効く** — 同じスロットの別チップに差し替えると結果が変わる
5. **衝突なし** — 注文どうしの完成形が同じにならない

完成形プレビューは `answer` を実際にSQLiteで実行して作るので、注文票の文面と完成形がずれることはない。

## 勝敗条件

- 勝利／敗北の概念はなく、60秒経過で終了しスコアを確定する
- スコア: 捌いた注文件数、最大コンボ、ミス回数を内訳として表示する

## MVPで作らないもの

- ウェーブ制サバイバルモード
- キーボードによる自由入力モード
- オンライン対戦、ランキング
- チップ配置のシャッフル、同時表示9枚以上のチップ
- JOIN（2テーブル目）、DISTINCT
