# QUERY RUSH 仕様書（SPEC）

作成日: 2026-11-16 / 改訂日: 2026-11-17（v2 採用）
ステータス: 仕様段階（v2 確定。「生産」ゲームから「認識」ゲームへ書き換え済み）

## 概要

UI Rush の骨格を SQL に移植した、4択で選ぶ認識ゲーム。

絞り込み前／後の小さなテーブルを見て、「どの `WHERE` でこうなったか」を固定4択チップで選ぶ。キーボードでクエリを書くことはしない。速さはマルチタスクではなく「データを読む判断の速さ」から作る。

## 共通前提

- DB は SQLite。候補 `WHERE` の実行は読み取り専用接続で行う
- 実行制限: 1クエリ 100ms / 取得上限 100行（画面表示は最大8行に絞る）
- 1プレイ完結型
- オンライン対戦・ランキングはMVP外

## なぜ v2 に書き換えたか（経緯）

2026-11-17、ユーザーの指摘：SQLゲーム6案は「勉強感・仕事感が強すぎて、ゲームとして手軽に楽しむには難しい」。
同じ日に確認した本人の既存作 UI Rush / Type Rush が「ゲームとしておもろい」理由は、SQL案に欠けていた次の4点だった：

1. **「思い出して作る」じゃなく「見て選ぶ」** — UI Rushはデモを触って4択から選ぶだけ、Type Rushは目の前の文を写すだけ。どちらも認識と反応のゲーム。SQL案は全部「正しいクエリを生産しろ」で、試験・仕事の形式そのものだった。
2. **間違いに寛容** — Type Rushは85%一致で合格、誤字でも止まらずその場で直せる。UI Rushも正誤表示中はタイマーが止まる。v1は「結果が完全一致したら提供」「ミスでコンボ切断」と正確さで締め上げていた。
3. **勉強要素が「遊んだ後」に来る** — UI Rushの解説は答えた後にタイマーを止めて読むもの。v1はスキーマ読み・条件読みという勉強部分を遊ぶ前に要求していた。
4. **スコアが生きている** — UI Rushは「いま正解したら何点か」が残り時間と一緒に減っていく。v1のフィードバックは正解／不正解の判定だけだった。

結論：発明し直す必要はなく、**UI Rushの骨格をそのままSQLに移植する**。QUERY RUSHのチップ形式が6案で一番この骨格に近かったため、本作を v2 化の対象とした。

## 変更の要旨（v1 → v2）

| v1（2026-11-16） | v2（2026-11-17 採用） |
|---|---|
| チップを並べてクエリを「生産」する | 絞り込み前／後のテーブルを見て、どの `WHERE` でこうなったかを4択で「選ぶ」 |
| 結果が注文と完全一致したら「提供」 | 1問＝1タップ回答。正解でも不正解でも次へ進む |
| ミスでコンボ切断 | ミスは速度ボーナス0・ストリークだけリセット。進行は止めない |
| スキーマ・条件文を文章で読む | データは色・形・行ハイライトで見せる。文章で読ませない |
| スコア＝基本点 × コンボ倍率 ＋ 残り時間ボーナス | UI Rush式：基本100 ＋ 速度ボーナス0〜100 ＋ ストリークボーナス0〜100（最大300／問）。取れる点が残り時間と一緒に減っていく |
| 60秒スプリント（捌いた注文件数） | 60秒タイムアタック（正解数と合計スコア） |
| 難化＝チップ種類の増加・JOIN | 難化＝データ側の罠（似た列名、NULL、重複行）。チップは常に4択 |

## 設計上の絶対条件（成立条件）

v1の絶対条件3点を、形を変えて維持する。実装時に崩してはならない。

1. **問題は常時1問だけ**（v1「注文は常時1件」から読み替え）。速さはマルチタスクではなく「データを読む判断の速さ」から作る。同時処理の忙しさは入れない（忙しいリアルタイム操作は好みに合わないため）
2. **4択スロットの位置は固定**（v1「チップ配置は固定」から読み替え）。探す時間ではなく、選ぶ時間で勝負させる
3. **表示するテーブルは最大8行・選択肢は4つ**（v1「同時表示チップ最大8枚」から読み替え）。難化は選択肢や行数の増加ではなく、データ側の罠（似た列名、NULL、重複行）で行う

## 画面構成

- 上段: 「絞り込み前 → 絞り込み後」の小さなテーブルを並べて表示（最大8行。変わった行はハイライトする。SQL文は出さない）
- 下段: `WHERE` チップ4枚（スロット位置は固定。選択肢の並びだけ変わる）
- 残り時間と「いま正解したら何点か」が見えること

## コアループ

1. 絞り込み前／後のテーブルが提示される
2. 「どの `WHERE` でこうなった？」に1タップで答える。制限時間は1問5秒（UI Rushと同じ3／5／8秒から選べる設定にする）
3. 正誤表示中はタイマーを止め、1行だけ解説を出す（例：「`status != 'returned'` は返品を除く。`price > 1000` だと安い行も残る」）。学びはここにだけ置く
4. 正解でも不正解でも次へ進む
5. 60秒経過で終了し、スコア・正解数・最大ストリーク・ミス回数を表示する

## スコア（UI Rush式）

- 1問あたり最大300点 ＝ 基本100 ＋ 速度ボーナス0〜100 ＋ ストリークボーナス0〜100
- 速度ボーナスは残り時間に比例して減る（「いま押せば何点か」が見えることが大事）
- 不正解・時間切れは0点でストリークリセット。ただしゲームは止まらない

## モード

- **60秒タイムアタック（MVPの中心）** — UI Rushと同じ枠組み
- **苦手復習** — 間違えたパターン（NULLの罠、似た列名など）だけをもう一度出す。UI Rushの苦手復習モードと同じ
- **リバース（MVP外でも可）** — `WHERE` を見せて「結果のテーブルはどれ？」を4択で選ぶ逆向きモード。UI Rushの逆引きと同じ発想

## データ設計（守ること）

- 1問のテーブルは小さく保つ（表示は最大8行）。読む量が増えた時点で仕事感に戻る
- 変化は「行の増減・ハイライト」で見せる。列名の読み比べを要求しない
- 罠はデータ側に置く：似た列名（`price` と `list_price`）、NULLの混入、重複行
- 4択の不正解は「惜しいもの」にする（例：`>` と `>=` の違い、等号の向き）。ランダムなダミーは出さない
- 生成条件：目標の絞り込み後テーブルは一意に定まること（4択のうち、正解の `WHERE` でだけその結果になること）を、候補 `WHERE` を実際に実行して検証する

## 勝敗条件

- 勝利／敗北の概念はなく、60秒経過で終了しスコアを確定する
- 内訳としてスコア・正解数・最大ストリーク・ミス回数を表示する

## MVPで作らないもの

- キーボードによる自由入力、クエリの組み立て（生産モード）
- JOIN・GROUP BY を扱う問題
- ウェーブ制サバイバル
- オンライン対戦、ランキング
- 4択スロット配置のシャッフル、9行以上のテーブル表示

## 未決事項

- 問題データの量産方法（手作りセット数十問から始めるか、生成ルールで作るか）
